## 三、RAG 主链路：5 个文件各自负责什么

### 3.1 `app/document_processer.py`（244 行）—— 把文件变成文本块

**职责**：整个链路的第一环，磁盘文件 → `Document` 对象列表。

| 函数 | 行号 | 作用 |
|---|---:|---|
| `load_document(file_path)` | 41 | 按后缀分派 Loader（PDF/TXT/MD/DOCX/HTML/CSV），返回 Document 列表 |
| `load_directory(dir_path)` | 128 | 递归遍历目录，逐个调 `load_document`，单个文件失败只跳过 |
| `clean_text(text)` | 174 | 去行首尾空白 + 删空行 |
| `split_documents(docs)` | 192 | 递归字符分块，产出最终入库的 chunk |

**关键概念**：
- **metadata 是溯源的基础**。每个 Document 带 `source`（路径）、`filename`、`page`（PDF 页码）、
  `start_index`（块在原文的位置）。后面 API 返回的"引用来源"全靠它。
- **chunk_size / chunk_overlap 是最值得调的参数**。太大夹带噪声，太小语义不全。
- **递归切分**：按 `["\n\n", "\n", "。", "；", " ", ""]` 从粗到细尝试，尽量在语义边界断开。

### 3.2 `app/vector_store.py`（724 行）—— 存取 + 检索

**职责**：向量库读写，以及混合检索的全部实现。**这是升级改动最大的文件。**

#### 第一块：向量化与连接

| `embedding_dim()` | 92 | 向量维度 |

#### 第二块：BM25 稀疏检索（新增）

| 函数 | 行号 | 作用 |
|---|---:|---|

**这是整个升级里最该理解的一块**：为什么 Milvus 存了文本，还要另存一份 JSONL？
—— 因为 Milvus 不提供"把全库文本拉出来建倒排索引"的高效接口。
这叫**倒排索引持久化**，是最简单可靠的做法。

#### 第三块：RRF 融合（新增）

| 函数 | 行号 | 作用 |
|---|---:|---|
| `rrf_fuse(rank_lists, top_k, weights)` | 457 | 多路结果按排名融合 |
| `_doc_key(doc)` | 438 | 去重键 = `source + md5(内容)`（**这里有个坑，见代码注释**） |

```
RRF 公式：score = Σ weight_i / (RRF_C + rank_i)     RRF_C = 60
```

**核心洞察**：稠密检索给余弦相似度（0~1），BM25 给无上界的词频分（可能 0.3 可能 27.5）。
**量纲不同不能直接相加**。RRF 只看排名不看分数，巧妙绕开了这个问题。

## 四、一次 `/query` 的完整旅程

把这条链路读懂，整个项目就通了。假设你问：**"Llama 2 的参数量是多少？"**

```
【1】main.py:368  query()
      │  收到 JSON，Pydantic 校验（不合法直接 422）
      ▼
【2】rag_chain.py:910  RAGChain.answer()
      │  填充初始 GraphState，交给状态图
      ▼
【3】rag_chain.py:444  transform_query
      │  QUERY_TRANSFORM=multi_query → LLM 裂变出 3 条查询：
      │     "Llama 2 的参数量是多少？" / "Llama 2 有多少参数？" / "LLaMA 2 parameter count"
      │  → state["queries"] = [4 条（含原问题）]
      ▼
【4】rag_chain.py:504  retrieve
      │  调 vector_store.py:552  multi_query_search(queries)
      │     ├─ 对每条查询：
      │     │    ├─ dense_search  → BGE 向量化 → Milvus 检索 Top-20
      │     │    └─ sparse_search → BM25 检索 Top-20
      │     │    └─ rrf_fuse 融合成一路
      │     └─ 再把 4 条查询的结果再 rrf_fuse 一次
      │  → state["documents"] = 融合后 20 条候选
      ▼
【5】rag_chain.py:527  rerank_documents
      │  Cohere Cross-Encoder 把「问题+每篇文档」拼起来重新打分
      │  20 条 → 只留最相关的 5 条（分数 0.87 / 0.80 / 0.73 / 0.69 …）
      │  （Cohere 挂了就跳过，透传原候选）
      ▼
【6】rag_chain.py:581  grade_documents
      │  LLM 逐条判断"这段能回答这个问题吗"，过滤无关的
      ▼
【7】决定路由（decide_after_grading）
      │  有相关文档 ────────────────► 去第 8 步
      │  全不相关 → rewrite_query 改写问题 → 回到第 3 步（最多 2 轮）
      ▼
【8】rag_chain.py:655  generate
      │  把 5 条文档拼成上下文 + 问题 → GLM 生成答案
      ▼
【9】rag_chain.py:699  check_groundedness
      │  让 GLM 当裁判：答案里每句话都能在文档里找到依据吗？
      │  ├─ 通过 → 结束
      │  └─ 不通过 → strict_grounding=True → 回第 8 步用严格提示词重写一次
      ▼
【10】main.py:222  _to_source()
      │  把 Document 转成 SourceInfo（含 relevance_score / rrf_score）
      ▼
【11】main.py:368  返回 QueryResponse
       answer + sources + queries + groundedness + …
```

**读代码时对着这条链路走一遍，每个函数的输入输出就都清楚了。**

## 五、学习路径建议

不要从 `vector_store.py` 第一行开始顺序读——724 行会看到睡着。按这个顺序：

### 第一站：先建立直觉（B 类，你自己写的）
```
LearnRAGv1.py      →  最朴素的 RAG 长什么样（检索→拼上下文→生成）
LearnMilvus.py     →  Milvus 怎么用
LearnHyDE.py       →  HyDE 是什么
```
这些你写过，看起来很轻松，但能帮你回忆"为什么要升级"。

### 第二站：看配置，建立全局观
```
app/config.py  →  只有 197 行，但有 35 个配置项
```
读完你就知道**这个系统有哪些可调的地方**，后面看代码时不会觉得突兀。

### 第三站：入口和出口
```
main.py            →  接口长什么样、返回什么
document_processer.py  →  数据从哪来
```
这两个文件没有复杂算法，先读完有安全感。

### 第四站：检索层（核心之一）
```
vector_store.py:
```

## 七、日常使用要注意的几件事

### 7.1 索引数据时：别直接跑 `/ingest/directory`

`data/` 下有 **66 个可索引文件**，其中 `data/uploads/` 是 56 个 SAR/海杂波方向的论文 PDF，
还包含多组 `(1)` `(2)` 后缀的**重复副本**；`data/chroma_db/` 里的旧实验残留也会被扫到。

而 `load_directory()` 用 `rglob("*")` **会递归扫描所有子目录**。后果：
- **非常慢**（CPU 上编码 60+ 个 PDF）
- **检索质量下降**（同一篇论文多个副本会占满 Top-K，挤掉其他信息）

**建议先单文件验证链路**：
```bash
curl -X POST http://127.0.0.1:8000/ingest/file -F "file=@data/paul_graham_essay.txt"
```

### 7.2 Embedding 模型是纯英文的（建议换）

```
EMBEDDING_MODEL=BAAI/bge-small-en-v1.5
```
`-en-` 表示**纯英文模型**。你那 56 篇论文是中文的，用英文模型索引 + 中文提问，
排序会明显偏。**建议换 `BAAI/bge-m3`**（多语言），但向量维度变了必须重建库：

```bash
# 1. .env 里改
EMBEDDING_MODEL=BAAI/bge-m3
MILVUS_DROP_OLD=true
# 2. 删掉旧的 BM25 语料副本
rm -f vector_db/bm25_corpus.jsonl
# 3. 重启 + 重新索引，完成后把 MILVUS_DROP_OLD 改回 false
```

### 7.3 每次改完代码，跑一下验收脚本

```bash
cd d:/project/llm/LangChainLearn
python _verify_after_merge.py
```
60+ 项检查，只读无副作用，最后给「✅ 全部通过」或列出问题。
**你自己改代码时尤其有用**——能立刻知道有没有改坏。

### 7.4 可以清理的东西（省磁盘，但删前确认）

| 路径 | 大小 | 说明 |
|---|---:|---|
| `vector_db/rag_index.faiss` + `.pkl` | ~37MB | **旧的 FAISS 索引，升级后已完全没用** |
| `data/chroma_db/`、`data/chroma_db_output/` | — | 早期 Chroma 实验残留，**会被 `/ingest/directory` 误扫** |
| `milvus_demo.db/` | — | `LearnMilvus.py` 的学习产物，与主链路无关 |
| `rag_eval/` | 空 | 空目录，评估功能已由 `eval_ragas.py` 承担 |
| `__pycache__/` | — | Python 缓存，可随时删 |

> `_backup_before_merge_20260912/` **不要删**——前面说过，它是你对照学习的最佳材料。

## 八、一句话总结

你原来的项目是**一条直线**：`问题 → 向量检索 → 生成`。

现在是一条**带纠错能力的流水线**：
```
查询变换 → 混合检索 → 精排 → 评分 ─┬─ 不相关 → 改写问题 ↺
                                    └─ 相关 → 生成 → 忠实性检查 ─┬─ 不过 → 重生成 ↺
                                                                  └─ 通过 → 答案
```

**升级的本质不是"加了几个新东西"，而是把"一次成型的直筒"改成了"可回退、可反思的流程"。**
读代码时抓这条主线，就不会迷失在细节里。
