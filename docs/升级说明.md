## 四、架构变化

### 升级前的图

```
retrieve -> grade_documents -> (无相关) rewrite_query -> retrieve（回环）
                             -> (有相关) generate -> check_groundedness -> END
```

### 升级后的图

```
transform_query -> retrieve -> rerank_documents -> grade_document
       ^                                                |
       |                                                v
  rewrite_query <-----(无相关文档且可重试)---------------+
       |
       +--(改写无效)--> generate --> check_groundedness --> END
```

新增三个环节，逐个说清它们在解决什么：

**1. `transform_query` —— 查询变换**

一个问题问法不好，后面精排再强也救不回来。这里按配置三选一：

| 模式            | 做法                                           | 适合场景    |
| ------------- | -------------------------------------------- | ------- |
| `none`        | 直接用原问题                                       | 调试基线    |
| `multi_query` | **RAG-Fusion**：裂变成 3~4 条不同角度的查询，各自检索后 RRF 融合 | 默认推荐    |
| `hyde`        | 让 LLM 先"编"一段假想答案，用假想答案去检索                    | 问题短、术语少 |

HyDE 的原理值得记一笔：问题→文档是**跨分布匹配**，而答案→文档是**同分布匹配**。  
用一段"长得像答案"的文本去检索，语义距离天然更近。

**2. `retrieve` —— 从单路向量检索升级为混合检索**

```
                    ┌─ 稠密：Milvus 向量检索 (Top 20) ─┐
    查询 ──────────┤                                  ├─ RRF 融合 ─> Top 20
                    └─ 稀疏：BM25 关键词检索 (Top 20) ─┘
```

为什么用 RRF 而不是加权求和：稠密相似度是余弦值（0~1），BM25 分数无上界（可能 0.3 也可能 27），  
**两者量纲完全不同，直接加权毫无意义**。RRF 只看"排第几"，天然免疫量纲问题：

```
score(doc) = Σ weight_i × 1/(60 + rank_i(doc))
```

中英文知识库实测效果：问 "GIL 是什么"，纯稠密检索把 `python.md` 排在第 1 位但把无关的  
`rerank.md` 也带进了 Top3；BM25 单独跑则精确命中 `python.md`。两路融合后 `hits` 字段会告诉你  
"这篇文档被几路同时命中"——多路都排前面的，才是真正该看的。

**3. `rerank_documents` —— 交叉编码器精排**

向量检索是双塔结构，问题和文档**分别**编码、从没见过面，快但粗；  
精排把 `[问题, 文档]` **拼在一起**送进模型，每个词都能和对方的词做注意力交互，准得多，  
代价是只能逐条打分。所以标准分工是：

> 向量检索负责"从百万里捞出一百"，精排负责"从一百里挑出五"。

顺序上精排刻意放在 `grade_documents` **之前**：文档评分要对每个文档调一次 LLM，  
先精排把 20 条砍到 5 条，LLM 调用次数直接降 4 倍。

## 五、RAGAs 评估怎么用

1. 在项目根目录建 `eval_set.json`：

```json
[
  {"question": "LangGraph 的状态图是怎么工作的？", "reference": "可选的标准答案"},
  {"question": "混合检索为什么用 RRF 融合？"}

```

1. 跑：

```bash

```

1. 指标怎么看：

| 指标低                 | 说明什么      | 去哪儿调                                       |
| ------------------- | --------- | ------------------------------------------ |
| `context_recall`    | 该找到的证据没找全 | chunk 大小、提高 `FUSION_TOP_K`、开 `multi_query` |
| `context_precision` | 捞了一堆没用的   | 调 `RERANK_TOP_N`、调 `DENSE/SPARSE_WEIGHT`   |
| `faithfulness`      | 模型在编      | 收紧 `GENERATE_PROMPT`、加强忠实性检查               |
| `answer_relevancy`  | 答案跑题      | 改生成模板                                      |

裁判 LLM 用的就是你项目里的 GLM。严格说"自己评自己"有偏向性，生产环境建议换一家模型当裁判。

## 六、实测发现的 4 个坑（都已修好）

### 坑 1：环境变量 `MILVUS_URI` 会让 `import pymilvus` 直接崩

pymilvus 3.x 的 `settings.Config` 里有：

```python
MILVUS_URI = str(os.getenv("MILVUS_URI", LEGACY_URI))
```

而 `pymilvus/orm/connections.py` 在**模块导入时**就会拿它去解析：

```python
address, parsed_uri = self.__parse_address_from_uri(Config.MILVUS_URI)
```

只要 `MILVUS_URI` 是本地文件路径，`import pymilvus` 就抛：

```
ConnectionConfigException: Illegal uri: [./vector_db/x.db],
expected form 'http[s]://[user:password@]example.com[:12345]'
```

注意是 **import 阶段就炸**，你还没调用任何 Milvus 接口。

**修法**：配置项改名 `RAG_MILVUS_URI` 绕开保留名；`config.py` 里另外加了一段防御，  
检测到非 http(s) 的 `MILVUS_URI` 会自动摘掉并打印提示。

### 坑 2：你的 ragas 0.4.3 一直是坏的，`import ragas` 就报错

ragas 0.4.x 在 import 时会执行：

```python
from langchain_community.chat_models.vertexai import ChatVertexAI
```

但 langchain-community 0.4.x 已经删掉了这个模块（Vertex 集成迁到了独立的  
`langchain-google-vertexai`）。于是：

```
ModuleNotFoundError: No module named 'langchain_community.chat_models.vertexai'
```

这也解释了你 9 月 4 日建的那个 `rag_eval/` 目录为什么是空的 —— 当时应该就是卡在这一步。

**修法**：`ChatVertexAI` 在 ragas 里只出现在一个 `isinstance` 类型清单里  
（判断模型支不支持一次返回多个候选），你用的是 GLM，永远走不到那个分支。  
所以 `eval_ragas.py` 里加了个 12 行的占位模块补丁，**不改 site-packages 里任何文件**，  
只在当前进程内生效。实测补丁后 ragas 0.4.3 的 5 个指标全部可用。

### 坑 3（我自己写出来的）：RRF 融合出现重复文档

第一版 `_doc_key()` 写的是"优先用 Milvus 主键 pk"。跑测试才发现是错的：

- 稠密检索走 Milvus，返回的 metadata 里**带** `pk`
- BM25 走的是本地语料副本，metadata 里**没有** `pk`

同一块文档两路算出的 key 不一样，融合时被当成两个不同结果，Top-K 里就出现了重复。  
测试输出里 `rrf.md` 连着出现两次、`rrf_score` 一模一样。

**修法**：统一用「来源 + 内容完整 md5」，与检索通路无关，三条路径算出的 key 必然一致。

### 坑 4（原有代码）：`settings.RECURSION_LIMIT` 根本不存在

你原来的 `app/rag_chain.py` 第 460 行：

```python
config={"recursion_limit": settings.RECURSION_LIMIT}
```

但 `app/config.py` 里没有定义 `RECURSION_LIMIT`。我实测 `getattr` 返回"不存在"——  
**这意味着你现在的 `/query` 接口一调用就抛 `AttributeError`**。  
新配置里补上了（默认 25）。

顺带修了 `main.py` 里的一处：

```python
raise HTTPException(status=422, detail=...)   # status 不是合法参数，会变成 TypeError
raise HTTPException(status_code=422, detail=...)  # 已修正
```

## 九、踩坑后的注意事项

1. **换 Embedding 模型 = 必须重建库**。向量维度一变，Milvus collection 结构就对不上。  
   把 `.env` 里 `MILVUS_DROP_OLD` 临时改成 `true`，重启一次，**然后立刻改回 `false`**，  
   否则每次重启都会清空知识库。
2. **`/ingest/directory` 是追加写入，不去重**。同一批文件重复调用会塞重复块。  
   要重来时先 `DELETE /index`，或直接把 `vector_db/` 删掉重来。
3. **BM25 语料副本不要单独删**。`vector_db/bm25_corpus.jsonl` 是稀疏检索的数据源，  
   删了之后 BM25 会静默失效（代码里做了兜底：BM25 不可用时自动退化为纯向量检索，  
   不会报错，所以更容易被忽略）。
4. **`/query` 的 LLM 调用次数变多了**。开启 `multi_query`(3) 后，一次提问大致是：  
   1 次查询变换 + 1 次改写(可能) + N 次文档评分 + 1 次生成 + 1 次忠实性检查。  
   想省钱就调小 `NUM_QUERIES`、调小 `RERANK_TOP_N`（评分次数跟着降）。
