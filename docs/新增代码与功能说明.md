## 二、整体架构：升级前 vs 升级后

### 升级前

```
问题 ──> BGE 向量化 ──> FAISS 单路检索 Top-K ──> 拼上下文 ──> GLM 生成 ──> 答案
```

问题在哪？三个短板：

1. **只有语义匹配**。专有名词、编号、缩写这类"字面精确匹配"的词，向量模型经常抓不住。
   比如你问 "SAR 相干斑抑制"，向量检索可能返回一堆讲"图像去噪"的段落，却没返回那篇标题就叫
   《SAR图像相干斑抑制算法研究》的论文。
2. **只有一次检索机会**。问题问得稍微口语化一点，检索就崩了，而且没有补救机制。
3. **没有防幻觉**。模型完全可以编一个答案，你无从判断它是真读到了还是瞎编的。

### 升级后

```
                        ┌─────────────────────────────────────────┐
                        │  rag_chain.py  LangGraph 状态图          │
                        └─────────────────────────────────────────┘

  问题
   │
   ▼
 ┌──────────────────┐   ① 查询变换：1 个问题 → N 条查询
 │ transform_query  │      multi_query：LLM 裂变出 3 条不同问法
 └────────┬─────────┘      hyde：让 LLM 先写"假想答案"，用它检索
          │
          ▼
 ┌──────────────────┐   ② 混合检索：每个查询同时走两条路
 │     retrieve     │      · 稠密路：BGE 向量 → Milvus 语义检索
 └────────┬─────────┘      · 稀疏路：BM25 关键词 → 词面精确检索
          │                · 两路结果用 RRF 融合（跨查询再融合一次）
          ▼
 ┌──────────────────┐   ③ 精排：Cohere Cross-Encoder 重新打分
 │ rerank_documents │      粗排 20 条 → 精排后只留 5 条喂给 LLM
 └────────┬─────────┘
          │
          ▼
 ┌──────────────────┐   ④ 相关度评分：逐条判断"这段真的能回答这个问题吗"
 │ grade_document   │
 └────────┬─────────┘
          │
    ┌─────┴──────────────────────────┐
    │ 有相关文档                      │ 全部不相关
    ▼                                ▼
 ┌──────────┐                ┌────────────────┐
 │ generate │                │ rewrite_query  │ ⑤ 改写查询，重新走一遍
 └────┬─────┘                └───────┬────────┘
      │                              │（最多 MAX_RETRIES=2 轮）
      │                              └──────> 回到 transform_query
      ▼
 ┌───────────────────┐  ⑥ 忠实性检查：答案是"文档里读出来的"还是"编的"？
 │ check_groundedness│     未通过 → 用严格提示词重生成一次（Self-RAG 反思闭环）
 └────────┬──────────┘     仍不通过 → 拒答："知识库中没有相关信息"
          ▼
        答案
```

**核心思想**：把"检索"从一次动作变成一条**可纠错、可反思的流水线**。每一步都能发现问题并回退重试，
而不是一条道走到黑。


#### 【修复】补上 `RECURSION_LIMIT`

```python
RECURSION_LIMIT: int = int(os.getenv("RECURSION_LIMIT", 25))
```

**这是一个必崩的 bug。** 你原来的 `rag_chain.py` 第 460 行用了 `settings.RECURSION_LIMIT`，
但 `config.py` 里从来没定义过这个属性。只要走到那行，立刻
`AttributeError: type object 'Settings' has no attribute 'RECURSION_LIMIT'`。

它控制 LangGraph 单次调用最多走多少步。必须满足
`RECURSION_LIMIT > 2 × (MAX_RETRIES + 1) + 3`，否则会抛 `GraphRecursionError`。
默认 25 对 MAX_RETRIES=2 来说很宽裕。

#### 【踩坑防御】`MILVUS_URI` 这个变量名有毒

这是踩过的一个真实的坑，值得单独讲：

```python
_reserved_uri = os.environ.get("MILVUS_URI", "")
if _reserved_uri and not _reserved_uri.startswith(("http://", "https://")):
    os.environ.pop("MILVUS_URI", None)
```

**原因**：`pymilvus` 的 `settings.Config` 里有这么一行：

```python
MILVUS_URI = str(os.getenv("MILVUS_URI", ""))
```

而 `pymilvus/orm/connections.py` 在**模块导入时**就解析它。
所以只要环境变量 `MILVUS_URI = ./vector_db/x.db`（本地路径），
`import pymilvus` 这一行就会直接抛：

```
ConnectionConfigException: Illegal uri: ['./vector_db/x.db'], expected form 'http[s]://...'
```

注意是 **import 阶段就炸**，还没等你调用任何 Milvus 接口。
这就是为什么本项目的配置项叫 `RAG_MILVUS_URI` —— 绕开这个保留名。
上面那段防御代码是兜底：万一你的系统环境里已经存在 `MILVUS_URI`，
先把它摘掉，避免污染 pymilvus。

#### 【降噪】压制 gRPC 心跳日志

```python
os.environ.setdefault("GRPC_VERBOSITY", "ERROR")
os.environ.setdefault("GRPC_GO_LOG_SEVERITY_LEVEL", "ERROR")
os.environ.setdefault("GRPC_GO_LOG_VERBOSITY_LEVEL", "ERROR")
```

Milvus Lite 内嵌了一个 gRPC 服务，默认会往终端狂刷
`WARNING too_many_pings ... GOAWAY` 这类心跳告警。它**不影响功能**，
但会把真正有用的日志淹没。这几个环境变量必须在 grpc 初始化之前设置，
所以放在 `config.py` 顶层（它是最早被导入的模块）。

**【修复】** `_detect_device()` 里原代码写的是 `{"device": " cpu"}` —— 注意 `cpu` 前面那个空格。
HuggingFace 在有些版本上会因此报 `RuntimeError: Expected one of cpu, cuda...`。已去掉。

#### 新增：BM25 稀疏检索

```python
def _append_corpus(docs)   # 把文档文本追加写入 bm25_corpus.jsonl
def _tokenize(text)        # 分词：jieba 优先，否则英文按词 + 中文单字 + 相邻二元组
def _load_bm25()           # 从语料副本重建 BM25 索引
def _bm25_search(query)    # BM25 检索
```

**为什么要"语料副本"这个文件？**
Milvus 只存向量和原文，但它不提供"把全库文本拉出来建 BM25 索引"的高效接口。
所以我们在写入时，顺手把文本追加到一个 JSONL 文件里，重启时从它重建 BM25。
这叫**倒排索引持久化**，是最简单可靠的做法。

**为什么要 jieba 分词？**
BM25 是纯词频统计，中文不分词的话整句话就是一个"词"，完全失效。
装了 jieba 就用它做专业分词；没装则降级为
「英文按单词切 + 中文按单字切 + 相邻两字组成二元组」，
二元组（bigram）能近似还原"相干斑""海杂波"这类词，属于不依赖第三方库的兜底方案。

#### 新增：RRF 融合

```python
RRF_C = 60

def rrf_fuse(rank_lists, top_k, weights=None) -> List[Document]
```

`RRF = Σ weight_i / (60 + rank_i)`

**RRF 解决什么问题？**
稠密检索给出的是**余弦相似度**（0~1），BM25 给出的是**无上界的词频分**（可能是 0.3，也可能是 27.5）。
这两个分数**量纲不同，不能直接加权相加** —— 相加等于让 BM25 单方面决定结果。

RRF 的巧妙之处：**只看排名，不看分数**。第 1 名得 1/61，第 2 名得 1/62……
这样两路检索天然可比。常数 60 是论文里的经验值，作用是让排名靠前的几档差距不至于过大。

**【踩坑修复】去重键**
```python
def _doc_key(doc) -> str:
    digest = hashlib.md5(doc.page_content.encode("utf-8")).hexdigest()[:16]
    return f"{doc.metadata.get('source', '')}|{digest}"
```

我第一版写的是"优先用 Milvus 主键 `pk` 去重"，结果融合结果里出现了大量重复块。
原因：**Milvus 通路返回的 Document 有 `pk`，BM25 通路（从 JSONL 重建的）没有 `pk`**，
导致同一个块在两条路上算出两个不同的 key，去重失效。

改成"source + 内容 MD5"后彻底解决 —— 这个键对两条通路都是稳定的。

**为什么不用 LangChain 官方的 `EnsembleRetriever`？**
LangChain 1.x 已经把 `langchain.retrievers` 这个模块**整个移除了**，
`EnsembleRetriever` 不复存在。而且它只支持"两路"，我们这里要支持
「N 条查询 × 2 条通路」的二维融合，自己实现 30 行反而更可控。

```python
def multi_query_search(queries, k=None, strategy="rrf") -> List[Document]
```

这是 RAG-Fusion 的实现。输入是 3~4 条查询，每条各自做一次混合检索，

#### 【修复】`DataNotMatchException: Insert missed an field 'producer'`

**这是你终端里那个 500 错误的真正原因。**

排查过程：
1. `POST /ingest/directory` 返回 500，报 `Insert missed an field 'producer'`；
2. `producer` 是 **PDF 的 metadata 字段**（pypdf 会写入 `producer` / `creator` / `creationdate` / `total_pages`），
   而 `.txt` / `.csv` 的 metadata 里没有这些字段；
3. 追到 `langchain_milvus` 的建表逻辑：`enable_dynamic_field=False`（默认值）时，
   它会**拿第一批文档扫到的所有 metadata key 建固定字段**；
4. `/ingest/directory` 会把 PDF、TXT、CSV 的块合并成**一个列表一次性入库**，
   建表时恰好扫到了 PDF 的 `producer`，把它固化成 Milvus 的固定字段；
5. 紧接着插入 `Data.csv` 的块 —— 它的 metadata 里没有 `producer`，
   Milvus 校验字段缺失，直接抛 `DataNotMatchException`。

**修复**：`enable_dynamic_field=True`。这个开关会把所有 metadata 塞进一个 `$meta` JSON 字段，
不再要求每批文档的 metadata 结构一致。向量检索本身完全不受影响，
检索结果的 `.metadata` 依然能正常读出来。

同时给 `add_documents()` 加了异常包装，万一以后还遇到类似问题，
报错信息会直接告诉你怎么办：

```python
except Exception as error:
    if "DataNotMatchException" in text or "missed an field" in text:
        raise RuntimeError(
            "...请 DELETE /index 或设置 MILVUS_DROP_OLD=true 后重启..."
        )
```

#### 【修复】Milvus Lite 文件锁死锁

```python
def _local_db_locked(db_path) -> bool
def _explain_milvus_open_failure(error) -> None
```

**现象**：`DataDirLockedError: Open local milvus failed`。

**原因**：Milvus Lite 对本地库文件加**独占锁**。如果你上一个服务进程没退干净
（或者开了两个终端跑同一个项目），第二个进程就打不开库。

**难点**：`milvus_lite` 内部把 `DataDirLockedError` 吞掉了，只在 stderr 打印，
Python 层的异常链里根本抓不到，没法用 `except` 判断。

**解法**：改**主动探测** —— 直接尝试对 LOCK 文件加锁，
Windows 用 `msvcrt.locking(..., LK_NBLCK, 1)`，Unix 用 `fcntl.flock`。
探测到占用就给出可操作的中文提示（附带 `netstat` / `taskkill` 命令），
而不是丢一堆英文堆栈给你。

#### 【修复】空库时刷 ERROR 堆栈

```python
def count() -> int:
    if not client.has_collection(settings.INDEX_NAME):   # ← 先判断
        return 0
    rows = client.query(..., filter="", output_fields=["count(*)"])
```

原来的实现直接去 `query`，库还不存在时 Milvus 会打一整页 ERROR 堆栈。
`/health` 接口每分钟被轮询一次，终端就被刷爆了。
加一行 `has_collection` 判断即可。

### 3.3 `app/rag_chain.py`（502 → 964 行）

#### 保留的部分

原来的 `grade_documents` / `rewrite_query` / `generate` / 条件路由全部保留，
连提示词都基本没动。这是一次**增量升级**，不是重写。

#### 新增节点 ①：`transform_query`

```python
def transform_query(state: GraphState) -> dict:
    # 三选一：none / multi_query / hyde
```

**multi_query（RAG-Fusion）**：让 LLM 把"LLM 参数量是多少"裂变成
"大语言模型的模型尺寸"、"LLM 有多少参数"、"大模型 parameter count" 等 3 条。
每条都去检索，最后融合。

**为什么有效？** 用户的问法和文档的写法经常对不上（口语 vs 书面、简称 vs 全称）。
与其赌一次，不如**广撒网**。这就是 `rag-from-scratch` 里 RAG-Fusion 那一节的核心思路。

**hyde**：让 LLM 先编一段"假想答案"，然后用**假想答案**去检索。
原理是：假想答案的用词风格和真实答案接近（都是陈述句、都包含专业术语），
而问题和答案之间是"跨分布"的。用答案检索答案，命中率更高。
（对应你的 `LearnHyDE.py`）

#### 新增节点 ②：`rerank_documents`

```python
def rerank_documents(state: GraphState) -> dict:
    reranker = get_reranker()
    reranked = reranker.compress_documents(documents=candidates, query=question)
```

**Bi-Encoder 和 Cross-Encoder 的区别（这是理解 Reranker 的关键）：**

- **Bi-Encoder（检索用的 BGE）**：问题和文档**分别**编码成向量，然后算余弦相似度。
  文档向量可以**离线算好存库**，所以快。但问题和文档之间没有交互，细粒度语义抓不住。
- **Cross-Encoder（Reranker）**：把 `[问题, 文档]` **拼在一起**送进模型，
  让注意力机制在两段文本之间充分交互。精度高得多，但**没法预计算** ——
  每来一个问题都要把候选文档全部重算一遍。

所以标准打法是**两阶段**：Bi-Encoder 粗排召回 20 条（快，从百万里捞），
Cross-Encoder 精排留 5 条（准，从 20 里筛）。这就是"召回-精排"架构。

实测效果：Cohere 精排后相关文档得分 `0.87 / 0.80 / 0.73 / 0.69`，
层次分明，不相关的直接被压到 0 分。

**【健壮性】失败降级**：Cohere 是**外部 API**，会超时、会限流、会欠费。

生成完答案后，再让 LLM 当一次裁判："这个答案的每一句，都能在检索到的文档里找到依据吗？"

**三档策略：**

| 取值 | 行为 | 适用场景 |
|---|---|---|
| `retry` | 失败 → **严格模式重生成** → 仍失败才拒答 | **默认，推荐** |
| `warn` | 失败 → 只打警告，保留原答案 | 宁可多给答案，也不要误拒 |
| `off` | 完全不检查 | 最省 token，但也失去防幻觉能力 |

#### 【重点修复】忠实性检查把正确答案判成幻觉

**这是你终端里反复出现的 `[warn] 答案未通过忠实性检查，替换为拒答`。**

排查过程值得记录，因为它非常反直觉：

1. 一开始怀疑是**语言错配**（英文文档 vs 中文答案），改了提示词要求"忽略语言差异"——
   **仍然判 no**；
2. 写诊断脚本把评分器的原始输出打出来，发现它每次都义正词严地说：
   "文档说上限从 7 billion 提升到 70 billion，即 70亿到 700亿；
   而答案说 70亿到 700亿……上限扩大了 10 倍，与文档不符"
   
   —— 等一下，**答案和文档的换算明明是正确**的（7 billion = 70亿，70 billion = 700亿）；
3. 做对照实验：**同一份答案，英文版判 `yes`，翻译成中文版判 `no`**；
4. 真相：**GLM 在跨语言数字换算时算错了**。
   它把 `70 billion` 误读成 `70亿`，然后拿这个错误的前提去指责一个正确答案"扩大了10倍"。

**这不是检索的问题，也不是答案的问题，是裁判自己算错了数学。**

**三处修复：**

**(a)** `GROUNDEDNESS_PROMPT` 里加入中英数量级换算对照表和正误示例：

```
1 thousand = 1千      1 million = 1百万
1 billion  = 10亿     1 trillion = 1万亿
```

并明确要求："进行数值比较前，必须先把两侧数值换算到同一数量级，
换算正确即视为一致，**不得因为表述语言不同而判定不一致**"。

**(b)** `GENERATE_PROMPT` 要求**数字原样引用、不做换算**：
文档里写 `70 billion` 就输出 `70 billion`，别自作主张换成中文单位。
从源头消除换算环节。

**(c)** 新增 `GENERATE_STRICT_PROMPT` + `regenerate` 条件边，
形成真正的 Self-RAG 闭环：第一次判决不过 ≠ 直接拒答，而是**换个更严格的提示词再写一遍**。

**验证结果**：修复后同一用例 → `评分器原始输出：'yes'  判定：通过` ✅

### 5.5 ⚠️ 索引时的重大注意事项

**先看一下 `data/` 目录里有什么。** 我实际统计了一下：

| 位置 | 内容 |
|---|---|
| `data/uploads/` | **56 个 PDF + 1 个 .xls**（SAR / 海杂波 / 舰船检测 / 遥感方向论文），含多组 `(1)` `(2)` 后缀的**重复副本** |
| `data/` 根目录 | `llama2.pdf`（13MB）、`paul_graham_essay.txt`、`Elon Musk.txt`、`Data.csv` 等 |
| `data/chroma_db/` | 旧实验残留的 2 个 PDF |
| `data/paul_graham/` | 与根目录 `paul_graham_essay.txt` **完全重复** |

**`data/` 下可被索引的文件合计 66 个。**

**而 `load_directory()` 用的是 `rglob("*")`，会递归扫描所有子目录。**

也就是说，直接调 `POST /ingest/directory` 会**一次性索引全部 66 个文件**，
其中包含大量重复论文。后果：

1. **非常慢** —— BGE-small 在 CPU 上编码 60+ 个 PDF（几百页），
   可能要几十分钟甚至更久；
2. **检索质量下降** —— 同一篇论文有 2~3 个副本，检索时会把
   "同一段话"重复占满 Top-K，挤掉真正不同的信息。

**建议做法**：先建一个小而干净的库跑通链路，再慢慢扩。

```bash
# 方案 A：只索引单个文件（推荐先这样验证）
curl -X POST http://127.0.0.1:8000/ingest/file \
  -F "file=@data/paul_graham_essay.txt"

# 方案 B：整理一个干净的子目录再整目录索引
mkdir -p data/clean
cp data/llama2.pdf data/paul_graham_essay.txt data/clean/
# 然后临时把 .env 的 DATA_DIR 指向 ./data/clean
POST /ingest/directory
```

如果你**确实要**索引全部 56 篇论文，建议先删掉带 `(1)` `(2)` 的重复文件。

### 7.1 ⚠️ 最该改的一件事：Embedding 模型是纯英文的

```
EMBEDDING_MODEL=BAAI/bge-small-en-v1.5
```

**换哪个？**

| 模型 | 维度 | 说明 |
|---|---:|---|
| `BAAI/bge-m3` | 1024 | **首选**，多语言（中英俱佳），支持长文本 |
| `BAAI/bge-small-zh-v1.5` | 512 | 纯中文，体积小、速度快 |
| `BAAI/bge-large-zh-v1.5` | 1024 | 纯中文，效果好但慢 |
