## 二、使用的原生 API 与 Agent SDK

本项目没有使用模型厂商专属的 Agent SDK，而是使用 **LangChain + LangGraph** 搭建 Agent，并通过 **OpenAI 兼容 API** 调用智谱 GLM。依赖约束以仓库中的 `requirements.txt` 为准，避免把某次本地安装版本误写成项目的固定版本。

| API / SDK | 项目中的用途 | 能力边界 |
|---|---|---|
| LangChain `create_agent`、`@tool` | 组装 ReAct Agent；根据函数签名、类型和 docstring 生成工具 Schema | 提供工具调用协议、消息组装和 Agent 运行骨架 |
| LangGraph `StateGraph`、`InMemorySaver` | 编排 7 节点 RAG 状态图；按 `thread_id` 保存多轮会话 | 提供状态合并、条件边、递归限制和 checkpoint 机制 |
| 智谱 GLM OpenAI 兼容 API | 查询变换、相关性评分、答案生成、忠实性判断和 Agent 决策 | 提供模型推理及 Function Calling；模型与地址由环境变量配置 |
| Tavily Search API | `search_web` 联网搜索工具 | 提供实时网页检索结果 |
| Cohere Rerank API | 对混合召回候选做交叉编码精排 | 是可选增强项；未配置或调用失败时透传原候选 |
| Hugging Face 本地 Embedding + Milvus | 文本向量化、存储和稠密召回 | Embedding 本地运行；Milvus 默认使用 Lite 文件模式 |
| Redis / Prometheus | LLM 响应缓存；接口 QPS、延迟、状态码和在途请求指标 | 属于工程基础设施，不参与 Agent 决策 |

关键选型考虑：

- OpenAI 兼容协议降低模型供应商耦合，RAG 与 ResearchAgent 共用同一组模型配置。
- 固定流程用 `StateGraph`，开放式研究任务用 `create_agent`，避免让 LLM 决定本来可以确定的业务步骤。
- 本地 Embedding 降低高频向量化的调用成本；Milvus Lite 便于本地演示，也可通过 URI 切换到服务端部署。
- Cohere、Tavily、Redis 都按“增强能力”设计，单项故障不会直接拖垮核心问答链路。

## 三、Agent Loop 与工具调用如何实现

### 3.1 第一层：可控的 Agentic RAG 状态图

`app/rag_chain.py` 使用 `GraphState(TypedDict)` 在节点间传递问题、候选文档、重试次数、生成结果和忠实性状态。主流程如下：

```text
START
  │
  ▼
transform_query → retrieve → rerank_documents → grade_document
                                                    │
                          ┌─────────────────────────┴────────────────────┐
                          │ 有相关文档                                    │ 无相关文档
                          ▼                                              ▼
                       generate ◀────────────── rewrite_query ──有变化→ transform_query
                          │                          │
                          ▼                          └─无变化/到达上限→ generate（兜底）
                check_groundedness
                          │
                  ┌───────┴────────┐
                  │ 通过/到达上限   │ 未通过且仍有额度
                  ▼                └──────────────→ generate（严格模式）
                 END
```

这层循环有两种自我修正：

1. **检索回环**：没有相关文档时改写查询并重新检索，`MAX_RETRIES` 限制次数。
2. **生成回环**：答案未通过忠实性检查时，用更严格的提示词重新生成，`MAX_GROUNDEDNESS_RETRIES` 限制次数。

`recursion_limit` 为整个图设置硬上限，防止错误路由或低质量结果造成无限循环。每个节点只返回需要更新的字段，由 LangGraph 合并状态，使路径和副作用都能单独观察。

### 3.2 第二层：自主选择工具的 ReAct Agent

`research_agent/agent.py` 通过 `create_agent` 注册两个异步工具：

| 工具 | 适用场景 | 项目实现 |
|---|---|---|
| `search_local_knowledge(query)` | 用户上传的论文、文档、笔记，需要文件名或页码出处 | 将第一层 `RAGChain.aanswer()` 整体封装为工具 |
| `search_web(query, max_results)` | 新闻、价格、版本等实时或公开信息；也用于交叉验证 | 调用 Tavily；结果条数限制在 1～5，每条正文按配置截断 |

一次工具调用的消息链路是：

```text
函数签名 + 类型注解 + docstring
        ↓  LangChain @tool
JSON Schema 随模型请求发送
        ↓
LLM 返回结构化 tool_calls（工具名、参数、调用 ID）
        ↓
LangChain 执行工具并生成 ToolMessage
        ↓
LLM 读取观察结果，继续选工具或输出最终回答
```

Agent 的一次 `ainvoke` 会重复 Reason → Act → Observe，直到模型返回不含 `tool_calls` 的 `AIMessage`，或触发 `recursion_limit`。`ResearchAgent._parse_trace()` 按 `tool_call_id` 关联调用与结果，形成可读的调试轨迹。

### 3.3 工具可靠性与会话设计

- **懒加载与隔离**：本地 RAG、Tavily 客户端都使用单例懒加载。只使用联网工具时不会预先加载 Embedding；本地库初始化失败也不会阻止 Agent 启动。
- **参数防御**：LLM 生成的 `max_results` 被夹在 `[1, 5]`，网页正文按字符数截断，避免非法参数和上下文膨胀。
- **失败可见**：`@resilient` 将异常分为临时错误和永久错误。超时、连接失败、限流等按指数退避重试；鉴权、配额和参数错误直接降级。
- **将错误返回给模型**：工具最终返回“原因、尝试次数、建议动作”的文本，而不是让异常中断整轮 Agent；模型可据此改用另一工具或向用户说明限制。
- **异步执行**：Agent 使用 `ainvoke`；Tavily 使用异步客户端；同步的模型加载和 Milvus 操作通过 `asyncio.to_thread` 移出事件循环。
- **会话记忆**：`InMemorySaver` 按 `thread_id` 隔离会话。它适合 Demo，但进程退出后会丢失；生产化可替换为持久化 checkpointer。

## 五、真实失败案例：忠实性检查误杀正确答案

### 5.1 现象

文档原文描述参数规模从 `7 billion` 增长到 `70 billion`，系统生成的中文答案是“从 70 亿增长到 700 亿”。答案和检索文档一致，但忠实性裁判返回 `no`，链路把正确答案替换为拒答。

这是一个典型的“守门机制自身出错”：检索和生成都正确，最终质量反而被 LLM 裁判拉低。

### 5.2 定位过程

1. **先隔离检索层**：增加 `/retrieve`，只执行查询变换、混合检索和精排，不生成答案。返回的原文块正确，因此排除召回问题。
2. **打开裁判黑盒**：记录评分器原始输出，而不只记录 `yes/no`。日志显示裁判把 `70 billion` 错误理解成 `70 亿`。
3. **做控制变量实验**：保持文档、事实和温度不变，只切换答案语言；英文版本通过、中文换算版本失败，将问题收敛到跨语言数量级判断。
4. **确认根因**：不是文档缺失，也不是答案幻觉，而是 LLM 裁判的数学换算错误。

### 5.3 修复

- **减少触发条件**：生成 Prompt 要求数字、单位和专有名词优先原样引用，并保留原文数值。
- **纠正裁判规则**：在 `GROUNDEDNESS_PROMPT` 中加入 `1 billion = 10 亿` 等换算规则及正反例，要求比较前统一单位。
- **增加申诉回环**：新增严格生成 Prompt。第一次判 `no` 时不立即拒答，而是严格重生成一次后再次检查；重试次数有硬上限。
- **防止再次回归**：验收脚本检查换算规则仍存在，并检查 `check_groundedness → generate` 回环可达。

### 5.4 验证证据

| 验证项 | 结果 |
|---|---|
| 原失败用例 | 项目故障记录显示修复后裁判输出 `yes`；记录见 `docs/新增代码与功能说明.md` |
| 图结构与防回归规则 | 2026-10-06 运行 `_verify_after_merge.py`，71/71 项通过 |
| 单元测试 | 2026-10-06 运行 `python -m unittest discover -s tests -v`，9/9 通过 |
| 在线端到端与 RAGAs | 仓库提供 `eval_ragas.py`；该项依赖模型/API Key 和网络，应在提交演示前用脱敏评估集重新运行并保存结果，不在本材料中虚构分数 |

Windows PowerShell 下验收脚本含 emoji，建议显式指定 UTF-8，避免 GBK 终端出现与业务无关的 `UnicodeEncodeError`：

```powershell

python _verify_after_merge.py
python -m unittest discover -s tests -v
```

这个案例让我形成了三条可复用经验：先用观测点隔离故障层级；LLM 裁判同样需要监控与回退；修复不仅要让原用例通过，还要把根因固化成自动化回归检查。
